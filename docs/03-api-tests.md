## 1. Общая картина

### Было → стало

**Было:** магазин работает (backend + база + сайт), но проверить его можно только руками: через Swagger или сайт.

**Стало:** отдельный Maven-модуль `tests/` и **144 автоматических API-теста**. Одна команда проверяет каталог, логин, корзину и заказы примерно за 30 секунд.

```
┌──────────────────┐   HTTP (JSON)    ┌─────────────┐      ┌────────────┐
│  tests/          │ ───────────────► │  backend    │ ───► │ PostgreSQL │
│  JUnit 5 +       │ ◄─────────────── │  :8080      │      │  :5432     │
│  REST Assured    │                  └─────────────┘      └────────────┘
└──────────────────┘        (запущены через docker compose)
```

Тесты **не запускают** backend сами. Они обращаются к уже работающему магазину по HTTP, как любой другой клиент (сайт, мобильное приложение, Postman). Это называется **тестирование чёрного ящика**: тесты знают только контракт API (адреса, JSON, коды ответов), а не внутренний код.

### Почему API-тесты пишут раньше UI-тестов

| | API-тест | UI-тест |
|---|---|---|
| Скорость | миллисекунды | секунды (браузер, отрисовка, ожидания) |
| Стабильность | высокая | ниже: анимации, задержки, локаторы |
| Что проверяет | бизнес-правила, коды ошибок, расчёты | что пользователь видит и может кликнуть |

Это «пирамида тестирования»: внизу много быстрых API-тестов, наверху немного медленных UI-тестов. Правила вроде «бесплатная доставка от $50» выгоднее проверять через API: 5 граничных значений за полсекунды вместо пяти прогонов браузера.

## 2. Структура модуля tests

```
tests/
├── pom.xml                                   ← зависимости модуля
└── src/test/
    ├── resources/
    │   └── allure.properties                 ← куда Allure пишет результаты
    └── java/com/shoplab/tests/
        ├── config/
        │   └── TestConfig.java               ← адрес API (из -D / переменной окружения / по умолчанию)
        ├── api/
        │   ├── Specs.java                    ← шаблоны запросов: базовый URL, JSON, токен, Allure
        │   ├── BaseApiTest.java              ← родитель всех тест-классов: сброс базы, помощники
        │   ├── client/                       ← API-клиенты («Page Object» для API)
        │   │   ├── ProductsClient.java
        │   │   ├── AuthClient.java
        │   │   ├── CartClient.java
        │   │   ├── OrdersClient.java
        │   │   └── TestSupportClient.java    ← ожидание health, сброс базы
        │   ├── model/                        ← JSON-тела запросов и ответов (records)
        │   │   ├── AuthModels.java
        │   │   ├── ProductModels.java
        │   │   ├── CartModels.java
        │   │   ├── OrderModels.java
        │   │   └── ErrorResponse.java
        │   ├── ProductsApiTest.java          ← 30 тестов
        │   ├── AuthApiTest.java              ← 35 тестов
        │   ├── CartApiTest.java              ← 42 теста
        │   └── OrdersApiTest.java            ← 37 тестов
        └── data/
            ├── TestData.java                 ← известные пользователи, товары, карты, адрес
            └── TestUsers.java                ← регистрация нового пользователя для теста
```

**Почему всё в `src/test`, а не в `src/main`?** В этом модуле нет кода приложения, только тесты. Maven запускает тесты из `src/test/java` командой `mvn test`, а все зависимости помечены `<scope>test</scope>`.

**Корневой `pom.xml`** теперь перечисляет два модуля: `backend` и `tests`. IntelliJ видит их оба.

| Библиотека | Версия | Зачем |
|---|---|---|
| **JUnit 5** (`junit-jupiter`) | 5.14.4 | Запускает тесты: `@Test`, `@BeforeEach`, `@ParameterizedTest`, `@Tag`, `@Nested` |
| **REST Assured** | 6.3.0 | Отправляет HTTP-запросы, проверяет ответы в стиле `given / when / then` |
| **Jackson** | 2.22.4 | Превращает Java-объекты в JSON и обратно; REST Assured находит его сам |
| **AssertJ** | 3.27.7 | Читаемые проверки: `assertThat(cart.total()).isEqualByComparingTo("79.98")` |
| **Allure** (`allure-junit5`, `allure-rest-assured`) | 2.35.6 | Собирает результаты для HTML-отчёта; каждый запрос и ответ прикрепляется к тесту |

**BOM (bill of materials)** — это список версий, проверенных вместе. В `pom.xml` импортированы `junit-bom` и `allure-bom`, поэтому у `junit-jupiter` и `allure-*` не нужно писать `<version>`.

> **Почему JUnit 5, а не JUnit 6?** JUnit 6 уже вышел, но план проекта и Cucumber (шаг 5) рассчитаны на JUnit 5. Код тестов в обеих версиях почти одинаковый (`org.junit.jupiter.api`), так что переход позже будет простым.

## 4. Слои: из чего состоит один тест

Возьмём тест «QA10 даёт скидку 10%» из `CartApiTest`:

```java
@Test
@DisplayName("QA10 gives 10% off the subtotal")
void qa10() {
    cart.addItem(Products.SELENIUM_BOOK, 2).then().statusCode(200);   // Arrange (подготовка)

    Cart body = expect(cart.applyPromo("QA10"), 200, Cart.class);     // Act (действие)

    assertThat(body.discount()).isEqualByComparingTo("8.00");         // Assert (проверка)
    assertThat(body.total()).isEqualByComparingTo("71.98");
}
```

Тест читается как сценарий: **AAA — Arrange, Act, Assert** (подготовить, сделать, проверить). В тесте нет ни URL, ни заголовков, ни JSON. Всё это спрятано в слоях ниже:

```
Тест (CartApiTest)          что проверяем: «QA10 даёт 8.00 скидки»
   │
   ▼
API-клиент (CartClient)     как вызвать: POST /api/cart/promo, тело {"code":"QA10"}
   │
   ▼
Спецификация (Specs)        общее для всех: http://localhost:8080, JSON, Bearer-токен, Allure
   │
   ▼
Конфигурация (TestConfig)   откуда взять адрес: -Dapi.url → SHOPLAB_API_URL → localhost:8080
```

Если завтра поменяется адрес эндпоинта, правится **одна строка** в клиенте, а не 40 тестов.

### TestConfig: адрес API без «зашитых» значений

```java
TestConfig.apiUrl()
```

Ищет значение по порядку:

1. системное свойство Java: `mvn test -Dapi.url=http://server:8080`;
2. переменная окружения: `$env:SHOPLAB_API_URL = "http://server:8080"` (удобно в CI);
3. по умолчанию: `http://localhost:8080`.

Те же тесты без изменений кода запускаются на ноутбуке, в GitHub Actions (шаг 7) или на тестовом сервере.

### Specs: шаблоны запросов

| Метод | Когда используется |
|---|---|
| `Specs.anonymous()` | Публичные эндпоинты: каталог, логин, регистрация, preview корзины |
| `Specs.withToken(token)` | Нужен логин: добавляет `Authorization: Bearer <token>`. При `token = null` заголовок не отправляется (для тестов на 401) |
| `Specs.technical()` | Служебные запросы вне тестов (ожидание health, сброс базы): **не** попадают в Allure |

Там же настроен Jackson:
- `NON_NULL` — поля со значением `null` не отправляются (запрос без карты = поле `card` отсутствует);
- `FAIL_ON_UNKNOWN_PROPERTIES = false` — если API добавит новое поле в ответ, старые тесты не сломаются.

## 5. API-клиенты: Page Object для API

В UI-тестах есть паттерн **Page Object**: класс-страница скрывает, *как* кликать (локаторы, ожидания), а тест говорит только, *что* сделать: `loginPage.loginAs(user)`.

Для API то же самое называется **API Client** (или **Service Object**). Каждый клиент отвечает за свою часть API:

| Клиент | Эндпоинты |
|---|---|
| `ProductsClient` | `GET /products`, `/products/{id}`, `/categories` |
| `AuthClient` | `POST /auth/register`, `/auth/login`, `/auth/logout`, `GET /users/me` |
| `CartClient` | всё под `/cart` + `preview` |
| `OrdersClient` | всё под `/orders` |
| `TestSupportClient` | `/actuator/health`, `POST /test/reset` |

Пример метода клиента:

```java
public Response applyPromo(String code) {
    return given()
            .spec(Specs.withToken(token))          // базовый URL, JSON, токен
            .body(new PromoRequest(code))          // Java-объект → JSON {"code":"QA10"}
            .when()
            .post("/api/cart/promo");
}
```

**Почему клиенты возвращают `Response`, а не сразу `Cart`?** Потому что тест должен уметь проверить *что угодно*: код ответа, тело ошибки, время ответа. В позитивном тесте `Response` превращается в `Cart`, в негативном — в `ErrorResponse`.

**Токен в конструкторе.** `CartClient` и `OrdersClient` создаются для одного пользователя:

```java
CartClient cart = new CartClient(token);
cart.addItem(7, 2);
cart.applyPromo("QA10");
```

Как Page Object, созданный для одной сессии браузера. `new CartClient(null)` — «незалогиненный» клиент для проверки 401.

## 6. Модели: JSON в виде Java-records

```java
public record AddItemRequest(Long productId, Integer quantity) { }
```

**Record** — короткая запись класса, который только хранит данные. Java сама создаёт конструктор, методы `productId()` / `quantity()`, `equals()` и `toString()`.

Jackson превращает record в JSON и обратно:

```
new AddItemRequest(7L, 2)   ⇄   {"productId": 7, "quantity": 2}
```

### Почему у тестов свои копии классов, а не классы backend

Тесты проверяют API **снаружи**. Если разработчик по ошибке переименует поле `total` в `totalPrice`, сайт сломается. Тест с собственной моделью тоже упадёт: `total` придёт `null`. А тест, который импортирует классы backend, переименуется вместе с ними и ничего не заметит.

### Мелкие, но важные решения

| Решение | Почему |
|---|---|
| `Integer` / `Long`, а не `int` / `long` в запросах | Чтобы негативный тест мог отправить `null` и проверить «Quantity is required» |
| `String` для `deliveryMethod`, `paymentMethod`, `status` | Чтобы отправить неизвестное значение `"ROCKET"` и проверить ошибку 400 |
| `BigDecimal` для денег | `double` неточен: `0.1 + 0.2 = 0.30000000000000004` |
| Методы `withZip(...)`, `withCard(...)` | Record нельзя изменить; `with...` возвращает копию с одним изменённым полем. Удобно для негативных тестов: «правильный заказ, но ZIP = 1234» |
| `Cart.item(productId)` | Найти строку корзины по товару или упасть с понятным сообщением |

## 7. Независимость тестов

Главное правило автотестов: **тест не должен зависеть от других тестов и от порядка запуска.** Иначе появляются «плавающие» (flaky) тесты: сегодня зелёные, завтра красные, хотя код не менялся.

В проекте это обеспечено тремя приёмами.

### 1) Сброс базы перед каждым тест-классом

```java
@BeforeAll
static void prepareEnvironment() {
    support.waitUntilApiIsHealthy();   // ждём, пока backend поднимется
    support.resetDatabase();           // POST /api/test/reset
}
```

`@BeforeAll` выполняется один раз перед всеми тестами класса. Каждый класс начинает с исходных данных: 25 товаров с исходным складом, 3 пользователя, без заказов.

**Почему не перед каждым тестом?** Сброс — это удаление и пересоздание всех таблиц. Перед каждым из 144 тестов это заметно замедлит прогон. Изоляцию внутри класса дают приёмы 2 и 3.

### 2) Новый пользователь для каждого теста корзины и заказов

```java
@BeforeEach
void newUserWithEmptyCart() {
    cart = new CartClient(TestUsers.registerNew().token());
}
```

Если бы все тесты использовали `standard@shoplab.test`, у них была бы **одна общая корзина**. Тест A кладёт товар, тест B ожидает пустую корзину и падает, но только если A выполнился раньше. Новый пользователь — это новая пустая корзина и пустая история заказов. Уникальный email: `user-3f9a1c2b@shoplab.test`.

### 3) Сравнение «до/после», а не с фиксированным числом

```java
int stockBefore = stockOf(Products.COFFEE_MAKER);
// ... заказ на 3 штуки ...
assertThat(stockOf(Products.COFFEE_MAKER)).isEqualTo(stockBefore - 3);
```

Если бы тест ожидал ровно `17`, он бы сломался, как только другой тест в том же классе купит кофеварку.

### Ожидание готовности API

Сразу после `docker compose up` backend стартует ещё несколько секунд. `waitUntilApiIsHealthy()` раз в секунду опрашивает `/actuator/health`, максимум 60 секунд. Если API так и не поднялся, тесты падают с понятным текстом:

```
The API at http://localhost:8080 is not healthy after 60 s. Is the shop running? Start it with: docker compose up -d
```

Это пригодится в CI (шаг 7).

## 8. Как писать проверки

### Два стиля

**Стиль 1. REST Assured + Hamcrest:** проверяем JSON напрямую, по пути к полю.

```java
products.getAll()
        .then()
        .statusCode(200)
        .body("totalItems", equalTo(25))
        .body("items", hasSize(8));
```

**Стиль 2. Превратить JSON в объект и проверить через AssertJ.**

```java
ProductPage page = expect(products.search(Map.of("page", 4)), 200, ProductPage.class);
assertThat(page.items()).hasSize(1);
```

В проекте используется в основном стиль 2: автодополнение в IntelliJ, проверка типов при компиляции, мощные проверки списков. Стиль 1 показан в `ProductsApiTest.firstPageHasEightProducts`, чтобы вы знали оба: на собеседованиях спрашивают про `given / when / then`.

### Помощники в BaseApiTest

| Метод | Что делает |
|---|---|
| `expect(response, 200, Cart.class)` | Проверяет код ответа и превращает тело в объект |
| `expectError(response, 409)` | Проверяет код ответа и общий формат ошибки (`status`, `timestamp`, `path`), возвращает `ErrorResponse` |

```java
assertThat(expectError(cart.addItem(Products.OUT_OF_STOCK, 1), 409).message())
        .isEqualTo("This item is out of stock");
```

### Полезные проверки AssertJ

| Проверка | Пример |
|---|---|
| Сравнение денег по значению | `isEqualByComparingTo("79.98")`. `isEqualTo` считает `79.98` и `79.980` разными |
| Одно поле у каждого элемента | `extracting(Product::category).containsOnly("Books")` |
| Порядок | `extracting(Product::price).isSortedAccordingTo(Comparator.naturalOrder())` |
| Условие для всех | `allSatisfy(p -> assertThat(p.inStock()).isTrue())` |
| Map ошибок полей | `containsEntry("quantity", "Quantity must be between 1 and 10")` |
| Пояснение в отчёте | `assertThat(body.shipping()).as("free shipping from $50")...` |
| Время ответа | `response.timeIn(MILLISECONDS)` ≥ 3000 для `slow@shoplab.test` |

## 9. Техники тест-дизайна в коде

### Граничные значения (boundary value analysis)

Правило: «стандартная доставка бесплатна, если сумма ≥ $50». Ошибки чаще всего живут на границе (`>` вместо `>=`), поэтому проверяем вокруг неё:

| Сумма | Как получена | Доставка | Тест |
|---|---|---|---|
| $49.98 | 2 × $24.99 | $5.99 (ещё $0.02 до бесплатной) | `justBelowFreeShippingLimit` |
| $50.00 | $32.00 + $18.00 | бесплатно | `exactlyAtFreeShippingLimit` |
| $54.99 − QA10 = $49.49 | скидка опускает сумму ниже границы | $5.99 | `qa10CanRemoveFreeShipping` |

Последний случай хитрый: $54.99 × 10% = 5.499, по правилу HALF_UP округляется до **5.50**. Тест одновременно проверяет и округление, и то, что граница считается **после** скидки.

Ещё границы: количество 0 / 1 / 10 / 11, склад «ровно 2 из 2» и «3 из 2», размер страницы 0 / 101.

### Параметризованные тесты

Один метод — много наборов данных:

```java
@ParameterizedTest(name = "quantity = {0}")
@ValueSource(ints = {0, -1, 11})
void quantityOutOfRange(int quantity) { ... }
```

Для нескольких параметров используется `@CsvSource`, где каждая строка — отдельный запуск:

```java
@CsvSource(delimiter = '|', value = {
        "sort     | cheap | Unknown sort 'cheap'. Allowed: featured, name, price-asc, price-desc, rating",
        "minPrice | -1    | Price cannot be negative",
})
```

В отчёте каждая строка видна как отдельный тест с понятным именем (`sort=cheap -> ...`). Добавить новый случай — значит добавить одну строку.

### @Nested: группы тестов

```java
@Nested
@DisplayName("Promo codes")
class PromoCodes { ... }
```

Вложенный класс группирует связанные тесты: в IntelliJ и в отчёте это отдельная «папка». `@BeforeEach` внешнего класса работает и для вложенного.

### Теги: запуск части тестов

| Тег | Что | Команда |
|---|---|---|
| `api` | все API-тесты (стоит на `BaseApiTest` и наследуется) | `-Dgroups=api` |
| `smoke` | 13 самых важных сценариев, около 8 секунд | `-Dgroups=smoke` |
| `slow` | логин `slow@shoplab.test` (3 секунды) | `-DexcludedGroups=slow` — пропустить |

## 11. Найденные баги

Тесты нашли **два настоящих бага в backend**. Оба исправлены.

### Баг 1. Один заказ — два разных `createdAt`

**Тест:** `OrdersApiTest.getOrderByNumber` — заказ, прочитанный через `GET`, должен совпадать с тем, что вернул `POST`.

```
POST /api/orders           → "createdAt": "2026-11-12T12:25:22.054530079Z"
GET  /api/orders/SL-818194 → "createdAt": "2026-11-12T12:25:22.054530Z"
```

**Причина:** часы Java дают время с точностью до **нано**секунд (9 цифр), а PostgreSQL хранит до **микро**секунд (6 цифр). `POST` возвращал значение из памяти Java, `GET` — из базы.

**Почему это важно:** клиент, который сравнивает или кеширует заказы по времени, увидит два разных заказа. Такие расхождения ловят именно API-тесты.

**Исправление** (`backend/.../order/Order.java`):

```java
this.createdAt = Instant.now().truncatedTo(ChronoUnit.MICROS);
```

### Баг 2. Сообщение об ошибке менялось от запроса к запросу

**Тест:** `AuthApiTest.registerValidation` с пустым именем. В первом прогоне прошёл, во втором упал. Это классический признак flaky-поведения.

Проверил 12 одинаковых запросов `{"name": ""}`:

```
5 раз  "name": "Name is required"
7 раз  "name": "Name must be at least 2 characters"
```

**Причина:** пустое имя нарушает сразу два правила: `@NotBlank` и `@Size(min = 2)`. Hibernate Validator возвращает нарушения в **случайном порядке**, а `GlobalExceptionHandler` брал первое попавшееся. На сайте порядок чёткий: сначала «обязательно», потом «длина» (`frontend/index.html`, функция регистрации).

**Почему это важно:** UI-тесты и API-тесты, которые ожидают «Name is required», падали бы случайно. Такой баг очень трудно поймать руками.

**Исправление** (`backend/.../common/GlobalExceptionHandler.java`): если у поля есть нарушение `@NotBlank` или `@NotNull`, показывается именно оно. После исправления 15 из 15 ответов одинаковые.

> **Урок:** если тест то падает, то проходит, не спешите писать «перезапустить». Сначала выясните, *что* меняется между запусками. Иногда нестабилен тест, а иногда, как здесь, сам продукт.

### Не баг, а ошибка в моём тесте

Тест `registerTrimsSpaces` ожидал, что API примет email с пробелами по краям (`"  user@shoplab.test  "`) и обрежет их. API ответил 400 «Enter a valid email address»: проверка формата выполняется **до** обрезки пробелов. Сайт обрезает пробелы сам перед отправкой, поэтому для пользователей всё работает. Я исправил тест: теперь один тест проверяет обрезку пробелов у имени, а второй фиксирует, что email с пробелами API отклоняет.

**Урок:** упавший тест — это повод разобраться, а не всегда баг. Ожидание в тесте тоже может быть неправильным.

## 12. Как запустить и проверить руками

### 1) Запустить магазин

Docker Desktop должен быть запущен. В PowerShell, в папке проекта:

```powershell

```

Ожидаемо: `shoplab-backend` и `shoplab-postgres` в статусе **healthy**. `--build` нужен, потому что на этом шаге изменился backend (исправления багов).

### 2) Запустить все тесты из терминала

```powershell
$env:JAVA_HOME = "$env:USERPROFILE\.jdks\openjdk-21.0.1"

```

```powershell
mvn -pl tests test -Dtest="CartApiTest#addItem"   # один тест
```

### 4) Запустить из IntelliJ

1. Если модуль `tests` не появился: откройте панель **Maven** справа и нажмите **Reload All Maven Projects** (круглые стрелки).

3. Откройте `tests/src/test/java/com/shoplab/tests/api/CartApiTest.java`.
4. Нажмите зелёный ▶ рядом с именем класса → **Run 'Cart API'**.

Внизу появится дерево тестов с группами **Shipping cost**, **Promo codes** и т. д. (это `@Nested` и `@DisplayName`). Правый клик по папке `api` → **Run 'Tests in api'** запускает все API-тесты.

Сломаем правило доставки и посмотрим, какие тесты это заметят.

## 14. Проблемы, которые встретились по пути

**1. Docker Desktop не был запущен.**
`failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`. Docker установлен не в `C:\Program Files\Docker`, а в `%LOCALAPPDATA%\Programs\DockerDesktop`. Запустил его оттуда.

**2. Шум в логе: `Could not add attachment: no test is running`.**
**Причина:** служебные запросы в `@BeforeAll` (ожидание health, сброс базы) проходили через фильтр Allure. Allure прикрепляет запрос к текущему тесту, а тест ещё не начался.
**Решение:** отдельная спецификация `Specs.technical()` без фильтра Allure для служебных запросов.

**3. Срок действия карты как «бомба замедленного действия».**
В тестовых данных легко написать `"expiry": "12/30"`, и в 2031 году все тесты заказов начнут падать сами по себе. Поэтому валидная дата вычисляется: `Cards.futureExpiry()` = сегодня + 2 года. Для негативных тестов формата используется `12/99`.

**4. Два бага backend и одна ошибка в тесте** — подробно в [разделе 11](#11-найденные-баги).

## 15. Словарик

| Термин | Простыми словами |
|---|---|
| **API-тест** | Тест, который отправляет HTTP-запросы к API и проверяет ответы, без браузера |
| **Чёрный ящик** | Тестирование снаружи: знаем входы и выходы, не смотрим во внутренний код |
| **REST Assured** | Java-библиотека для API-тестов в стиле `given / when / then` |
| **Request specification** | Шаблон запроса: базовый URL, заголовки, фильтры, общие для многих запросов |
| **API Client / Service Object** | Класс, скрывающий детали вызова эндпоинтов; аналог Page Object для API |
| **Page Object** | Класс-страница в UI-тестах: скрывает локаторы и действия на странице |
| **Record** | Короткая запись Java-класса, который только хранит данные |
| **Сериализация / десериализация** | Java-объект → JSON / JSON → Java-объект |
| **BOM** | Список согласованных версий библиотек, импортируемый в `pom.xml` |
| **AAA** | Arrange, Act, Assert: подготовка, действие, проверка — структура теста |
| **Фикстура** | Подготовка окружения для теста: `@BeforeAll`, `@BeforeEach` |
| **Flaky-тест** | Нестабильный тест: то проходит, то падает без изменений кода |
| **Граничные значения** | Техника тест-дизайна: проверяем значения на границе правила и рядом с ней |
| **Параметризованный тест** | Один тестовый метод, который запускается с разными наборами данных |
| **Тег** | Метка теста (`smoke`, `slow`) для запуска выбранной группы |
| **Smoke-тесты** | Небольшой быстрый набор самых важных проверок: «работает ли вообще» |
| **Пирамида тестирования** | Много быстрых низкоуровневых тестов, мало медленных UI-тестов |
| **Surefire** | Maven-плагин, который запускает тесты при `mvn test` |
| **Позитивный / негативный тест** | Проверка правильного сценария / проверка реакции на неправильные данные |
