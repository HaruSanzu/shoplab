## 1. Общая картина

Интернет-магазин удобно представить как ресторан:

| Часть | В ресторане | В ShopLab | Где лежит |
|---|---|---|---|
| **Frontend** | Зал и меню, то, что видит гость | Сайт в браузере | `frontend/` |
| **Backend** | Кухня, где заказы выполняются по правилам | Java-программа (REST API) | `backend/` |
| **База данных** | Склад, где всё хранится | PostgreSQL, таблицы | запускается в Docker |

### Было → стало

**Было:** только сайт. Все данные (корзина, пользователи, заказы) хранились в `localStorage`, то есть в памяти конкретного браузера. Сервера и базы не было, проверять можно было только интерфейс.

**Стало:** настоящий сервер и настоящая база данных. Теперь можно писать тесты на **трёх уровнях**:

| Уровень | Инструмент | Что проверяем |
|---|---|---|
| UI | Selenium + Cucumber | Пользователь кликает по сайту, всё работает |
| API | REST Assured | Сервер правильно отвечает на запросы |
| База данных | JDBC | В таблицах лежат правильные данные |

Именно такое сочетание ожидают увидеть в портфолио QA Automation Engineer.

## 3. База данных и Flyway

### Таблицы

| Таблица | Что хранит | Пример |
|---|---|---|
| `products` | 25 товаров | Wireless Headphones X200, $79.99, на складе 15 |
| `users` | Пользователи | standard@shoplab.test |
| `auth_tokens` | «Пропуска» залогиненных пользователей | токен → пользователь |
| `carts` | Корзина пользователя + промокод | у каждого пользователя одна |
| `cart_items` | Товары в корзине | товар 7, 2 штуки |
| `orders` | Заказы | SL-181961, PROCESSING, $63.97 |
| `order_items` | Строки заказа | товар, цена на момент покупки, количество |

Связи между таблицами:

```
users ──< auth_tokens          (у пользователя может быть несколько токенов)
users ──  carts ──< cart_items >── products
users ──< orders ──< order_items >── products
```

`──<` значит «один ко многим»: у одного заказа много строк.

### Что такое Flyway и зачем он нужен

Таблицы **не создаются руками**. Их создают SQL-файлы — **миграции**:

| Файл | Что делает |
|---|---|
| `V1__create_schema.sql` | Создаёт все таблицы |
| `V2__seed_data.sql` | Заполняет их тестовыми данными: 25 товаров и 3 пользователя |

При каждом запуске backend Flyway делает следующее:

1. Смотрит в служебную таблицу `flyway_schema_history`: какие файлы уже выполнены.
2. Выполняет новые файлы по порядку номеров.
3. Записывает их в `flyway_schema_history`.

**Зачем:** база у вас, в GitHub Actions и у любого, кто скачал проект, всегда одинаковая. Структура базы хранится в git, как и код.

> ⚠️ **Главное правило:** уже выполненный файл миграции **нельзя менять**. Если нужно изменить базу, создайте новый файл: `V3__add_something.sql`.

### Полезные детали в схеме

- **`CHECK`-ограничения**, например `stock >= 0` или `quantity BETWEEN 1 AND 10`. Даже если в коде будет ошибка, база не позволит записать отрицательный склад.
- **Уникальный email без учёта регистра**: `A@test.com` и `a@test.com` считаются одним аккаунтом.
- **Цена в заказе копируется.** В `order_items` хранится название и цена **на момент покупки**. Если товар потом подорожает, старые заказы не изменятся. Так работают настоящие магазины.
- **Пароли тестовых пользователей хешируются прямо в SQL** с помощью расширения PostgreSQL `pgcrypto`: `crypt('Password123', gen_salt('bf'))`. Получается тот же формат BCrypt, который проверяет Java.

## 4. Backend: как устроен код

### Технологии

| Что | Зачем |
|---|---|
| **Java 21** | Язык |
| **Spring Boot 4** | Фреймворк: веб-сервер, работа с базой, настройки. Многое делает «из коробки» |
| **Spring Data JPA / Hibernate** | Работа с базой через Java-объекты, а не через ручной SQL |
| **Bean Validation** | Проверка входных данных аннотациями (`@NotBlank`, `@Pattern`) |
| **Flyway** | Миграции базы |
| **springdoc (Swagger UI)** | Интерактивная документация API |
| **spring-security-crypto** | Только BCrypt для паролей, без всего Spring Security |
| **Actuator** | Эндпоинт `/actuator/health`: «я жив» |

### Код разложен по функциям магазина

В каждой папке (`product`, `cart`, `order`, `auth`) лежат одни и те же типы классов:

| Класс | Роль | Аналогия | Пример |
|---|---|---|---|
| **Controller** | Принимает HTTP-запрос и отдаёт ответ. Ничего не решает сам | Официант | `CartController` |
| **Service** | Бизнес-логика, все правила | Повар | `CartService` |
| **Repository** | Чтение и запись в базу | Кладовщик | `CartRepository` |
| **Entity** | Java-класс = строка таблицы | Продукт на складе | `Cart`, `CartItem` |
| **DTO** | Что уходит наружу в виде JSON | Тарелка, которую несут гостю | `CartDto` |

**Почему так:** у каждого класса одна задача. Правило «нельзя купить больше, чем есть на складе» живёт только в `CartService`, и его легко найти и изменить.

**Почему DTO, а не Entity:** если отдавать сущности напрямую, наружу может утечь лишнее (например, хеш пароля), а любое изменение в базе сломает API. С DTO база и API меняются независимо.

### Repository: SQL пишет Spring

Посмотрите на `UserRepository.java`:

```java
Optional<User> findByEmailIgnoreCase(String email);
```

Реализации у этого метода нет, Spring **сам** строит SQL по имени метода:
`find` + `By` + `Email` + `IgnoreCase` → `where upper(email) = upper(?)`.

## 5. Путь одного запроса от начала до конца

Пример: пользователь добавляет в корзину 2 книги «Selenium in Practice».

```
POST http://localhost:8080/api/cart/items
Authorization: Bearer 26e1142d...
{"productId": 7, "quantity": 2}
```

**Шаг 1. `CurrentUserArgumentResolver`** читает заголовок `Authorization`, ищет токен в таблице `auth_tokens` и находит пользователя. Если токена нет — ответ **401**, дальше запрос не идёт.

**Шаг 2. `CartController.addItem(...)`** получает тело запроса. Аннотация `@Valid` проверяет правила из `AddItemRequest`: `quantity` от 1 до 10. Если правило нарушено — ответ **400**.

**Шаг 3. `CartService.addItem(...)`** проверяет бизнес-правила:
- товар существует? Нет → **404**;
- товар есть на складе? Нет → **409** «This item is out of stock»;
- уже в корзине + новое количество ≤ склада? Нет → **409** «Only N item(s) available in stock».

**Шаг 4. Repository + Hibernate** записывают изменения в таблицу `cart_items`.

**Шаг 5. `PriceCalculator`** считает итоги: 2 × $39.99 = $79.98, это ≥ $50, значит доставка бесплатная.

**Шаг 6. Ответ уходит в JSON:**

```json
{
  "items": [{ "productId": 7, "title": "Selenium in Practice", "unitPrice": 39.99, "quantity": 2, "lineTotal": 79.98 }],
  "itemCount": 2,
  "subtotal": 79.98,
  "discount": 0.00,
  "shipping": 0.00,
  "total": 79.98
}
```

Если на любом шаге что-то пошло не так, сервис бросает `ApiException`. Её ловит `GlobalExceptionHandler` и превращает в аккуратный JSON с ошибкой (см. ниже).

> 💡 **@Transactional** (стоит над сервисами): все изменения в базе внутри метода сохраняются **вместе** или **не сохраняются вовсе**. Например, при оформлении заказа не может получиться, что заказ создан, а склад не уменьшился.

## 6. Важные решения внутри backend

### 🔐 Логин через токен

1. Вы отправляете email и пароль на `POST /api/auth/login`.
2. Сервер проверяет их, создаёт случайный токен (64 символа), сохраняет его в `auth_tokens` и возвращает вам.
3. Во всех следующих запросах вы отправляете заголовок `Authorization: Bearer <токен>`.
4. `POST /api/auth/logout` удаляет токен из базы, и он перестаёт работать.

Чтобы не разбираться пока с большим фреймворком Spring Security, сделан простой механизм: аннотация `@CurrentUser`. Если в методе контроллера есть параметр `@CurrentUser User user`, этот эндпоинт требует логина.

**Особые пользователи:**
- `locked@shoplab.test`: пароль верный, но ответ **403** «account has been locked».
- `slow@shoplab.test`: логин специально занимает **3 секунды**, чтобы тренировать ожидания (waits) в тестах.
- На «нет такого email» и «неверный пароль» сервер отвечает одинаково: «Invalid email or password». Так злоумышленник не узнает, какие email зарегистрированы.

### 🔒 Пароли хранятся как хеш (BCrypt)

В базе лежит не `Password123`, а `$2a$10$xK...`. Из хеша пароль восстановить **нельзя**, можно только проверить, совпадает ли он.
👉 Хорошая идея для будущего JDBC-теста: «после регистрации пароль в базе не хранится в открытом виде».

### ✅ Валидация с теми же текстами, что на сайте

Все сообщения скопированы из `frontend/index.html`. Например, неверный ZIP-код и на сайте, и в API даёт «ZIP code must be 5 digits».
👉 UI-тесты и API-тесты смогут проверять **одинаковые** тексты ошибок.

### ❌ Единый формат ошибок

Любая ошибка выглядит одинаково (класс `ErrorResponse`):

```json
{
  "timestamp": "2026-11-11T15:17:56Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "path": "/api/orders",
  "fieldErrors": {
    "shippingAddress.zip": "ZIP code must be 5 digits",
    "shippingAddress.phone": "Enter a valid phone number"
  }
}
```

Всё это собирает `GlobalExceptionHandler`. Он ловит **любую** ошибку и приводит её к этому виду. Неожиданные ошибки (баги) он записывает в лог, а клиенту отвечает «Unexpected server error» без технических подробностей.

### 📟 Коды ответов

Именно их вы будете проверять в API-тестах:

| Код | Значение | Когда |
|---|---|---|
| **200** OK | Успех | Почти все GET и изменения корзины |
| **201** Created | Создано | Регистрация, оформление заказа |
| **204** No Content | Успех без тела ответа | Логаут |
| **400** Bad Request | Неверные данные | Пустое поле, неверный ZIP, неизвестный промокод |
| **401** Unauthorized | Не залогинен | Нет токена, неверный токен, неверный пароль |
| **402** Payment Required | Платёж отклонён | Карта `4000 0000 0000 0002` |
| **403** Forbidden | Доступ запрещён | Заблокированный аккаунт |
| **404** Not Found | Не найдено | Нет товара, нет заказа, **чужой** заказ |
| **409** Conflict | Конфликт состояния | Нет на складе, заказ уже отменён, email занят |

> Почему чужой заказ отдаёт 404, а не 403: так мы не раскрываем, что заказ с таким номером вообще существует.

### 💰 Деньги в `BigDecimal`, а не в `double`

В `double` выражение `0.1 + 0.2` равно `0.30000000000000004`. Для денег это недопустимо. Поэтому в Java используется `BigDecimal`, а в базе тип `NUMERIC(10,2)`.

Все правила цен лежат в **одном** месте, `pricing/PriceCalculator.java`:

| Правило | Значение |
|---|---|
| `QA10` | Скидка 10% от суммы товаров (округляется до центов) |
| `FREESHIP` | Бесплатная стандартная доставка |
| Стандартная доставка | Бесплатно, если (сумма − скидка) ≥ $50, иначе $5.99 |
| Экспресс-доставка | Всегда $9.99 |
| Пустая корзина | Всё $0 |

Пример из ручной проверки: книги на $59.98 + QA10 → скидка $6.00 → $53.98 ≥ $50 → доставка бесплатная → **итого $53.98**. С экспресс-доставкой: 59.98 − 6.00 + 9.99 = **$63.97**.

### 📦 Склад

- При оформлении заказа `stock` товаров **уменьшается**.
- При отмене заказа **возвращается**.
- Отменить можно только заказ в статусе `PROCESSING`. Повторная отмена → **409**.

👉 Отличный сценарий для теста базы: «оформил заказ → stock уменьшился → отменил → stock вернулся».

### 💳 Оплата картой

Проверки такие же, как на сайте: номер из 16 цифр (пробелы и дефисы допускаются), срок `MM/YY` и не в прошлом, CVV из 3 цифр. В базе хранятся **только последние 4 цифры** карты (`card_last4`), полный номер никогда не сохраняется.

### 🧹 Сброс базы для тестов

`POST /api/test/reset` стирает всю базу и заново выполняет миграции V1 и V2. После этого снова 25 товаров с исходным складом, 3 пользователя, ни одного заказа.

**Зачем:** хороший автотест **не зависит от других тестов**. Каждый тест (или набор тестов) может начинать с одинаковых чистых данных.

Эндпоинт включается настройкой `SHOPLAB_TEST_ENDPOINTS=true`. В настоящем магазине такого быть не должно, это специально для учебного проекта.

### 🌐 CORS

Браузер по умолчанию **запрещает** сайту с `localhost:3000` обращаться к API на `localhost:8080` (это разные «источники»). В `WebConfig` API явно разрешает такие запросы. Это понадобится на шаге 2, когда сайт начнёт ходить в API.

### ⚙️ Настройки (`application.yml`)

Значения записаны в виде `${DB_URL:jdbc:postgresql://localhost:5432/shoplab}`. Это значит: «возьми переменную окружения `DB_URL`, а если её нет, используй значение после двоеточия».
- Запускаете локально из IntelliJ → используются значения по умолчанию (`localhost`).
- Запускаете в Docker → `docker-compose.yml` подставляет свои (`postgres` вместо `localhost`).

Код при этом менять не нужно.

Ещё одна важная настройка: `ddl-auto: validate`. Hibernate **не создаёт и не меняет** таблицы, это работа Flyway. Hibernate только проверяет при старте, что Java-классы совпадают с таблицами, и не запускается, если нашёл расхождение.

## 7. Docker и docker-compose

### Основные понятия

| Термин | Что это |
|---|---|
| **Образ (image)** | Упакованная программа со всем необходимым: Java, библиотеки, ваш код. Как установочный диск |
| **Контейнер** | Запущенный образ. Как маленький отдельный компьютер |
| **Dockerfile** | Рецепт сборки образа |
| **docker-compose.yml** | Описание нескольких контейнеров, которые работают вместе |
| **Volume** | Папка для данных, которая переживает перезапуск контейнера |

### `backend/Dockerfile`: сборка в два этапа

1. **Этап сборки:** образ с Maven и JDK компилирует код и собирает `shoplab-backend.jar`.
2. **Этап запуска:** в итоговый образ кладётся **только** готовый `.jar` и Java для его запуска.

Так итоговый образ меньше и не содержит исходников и Maven. Сначала копируется только `pom.xml` и скачиваются зависимости: Docker кэширует этот слой, и при изменении кода библиотеки повторно не скачиваются.

### `frontend/Dockerfile`

Сайт — это статичный HTML, поэтому ему нужен только веб-сервер. Используется **nginx**, который просто отдаёт `index.html`.

### `docker-compose.yml`: три контейнера

```
┌──────────────┐  healthy?   ┌──────────────┐  healthy?   ┌──────────────┐
│   postgres   │ ──────────▶ │   backend    │ ──────────▶ │   frontend   │
│  порт 5432   │             │  порт 8080   │             │  порт 3000   │
└──────────────┘             └──────────────┘             └──────────────┘
```

- **Порядок запуска:** backend ждёт, пока база станет «healthy», а frontend ждёт backend.
- **Healthcheck** — регулярная проверка, что сервис действительно работает:
  - postgres: команда `pg_isready` («принимаешь подключения?»);
  - backend: запрос к `/actuator/health` («ответь UP»).
- **Порты** `"8080:8080"` означают «порт на вашем компьютере : порт внутри контейнера». Сайт внутри контейнера работает на 80, а снаружи доступен на 3000.
- **Внутри Docker-сети** контейнеры обращаются друг к другу по имени: backend подключается к `postgres:5432`, а не к `localhost`.
- **Volume `pgdata`**: данные базы сохраняются, даже если контейнер остановить.

**Почему Docker:**
1. Не нужно устанавливать PostgreSQL на Windows.
2. На шаге 7 GitHub Actions запустит **ровно то же самое** одной командой.

## 12. Проблемы, которые встретились по пути

Ошибки — нормальная часть работы, и на каждой можно чему-то научиться.

**1. Не удалось перенести папку `frontend`** («Device or resource busy»).
**Причина:** Windows не даёт перемещать папку, пока её использует другой процесс (терминал или IntelliJ).
**Решение:** скопировал файлы, проверил, что копия совпадает с оригиналом, и удалил старую папку.

**2. Backend не запустился: ошибка в миграции V2.**
```
ERROR: duplicate key value violates unique constraint "products_sku_key"
```
**Причина:** сначала я вставлял товары с пустым SKU (`''`), чтобы заполнить его позже. Но колонка `sku` уникальная, и второй пустой SKU база отвергла.
**Что важно:** Flyway **откатил всю миграцию целиком**, и приложение не запустилось. Наполовину заполненной базы не осталось. Так и задумано: лучше упасть сразу, чем работать с испорченными данными.
**Решение:** вписал SKU явно (`SL-00001`, `SL-00002`, …).

**3. Docker Desktop не был запущен.**
Команда `docker` была установлена, но сам Docker не работал. Запустил Docker Desktop, после этого всё заработало.

## 13. Словарик

| Термин | Простыми словами |
|---|---|
| **API** | Набор адресов, по которым программы обмениваются данными |
| **REST** | Стиль API: ресурсы (`/products`, `/orders`) + HTTP-методы (GET читать, POST создать, PUT изменить, DELETE удалить) |
| **Эндпоинт** | Конкретный адрес API, например `GET /api/products` |
| **JSON** | Текстовый формат данных: `{"name": "value"}` |
| **HTTP-статус** | Число в ответе, которое говорит, чем закончился запрос (200, 404…) |
| **Миграция** | SQL-файл, который меняет структуру базы, с номером версии |
| **Entity** | Java-класс, отражающий строку таблицы |
| **DTO** | Объект, который отправляется наружу в виде JSON |
| **Repository** | Интерфейс для работы с базой; реализацию пишет Spring |
| **Service** | Класс с бизнес-логикой |
| **Controller** | Класс, который принимает HTTP-запросы |
| **Транзакция** | Группа изменений в базе: сохраняются все вместе или ни одно |
| **Хеш** | Необратимое «отпечатывание» данных; так хранят пароли |
| **Токен** | Случайная строка-пропуск, подтверждающая, что вы залогинены |
| **Healthcheck** | Регулярная проверка «сервис жив и работает?» |
| **CORS** | Правило браузера, какие сайты могут обращаться к API |
| **Swagger / OpenAPI** | Автоматическая документация API, где можно отправлять запросы |
