## 1. Общая картина

### Было → стало

**Было (после шага 1):** backend и база уже работали, но сайт их **не использовал**. Список товаров был «зашит» прямо в JavaScript, а пользователи, корзина и заказы хранились в `localStorage` браузера. По сути, два независимых приложения.

**Стало:** сайт берёт данные из API.

```
                 HTTP-запросы (fetch)                  SQL
┌───────────┐  ───────────────────────▶  ┌──────────┐ ─────▶ ┌────────────┐
│  Браузер  │   GET /api/products         │ Backend  │        │ PostgreSQL │
│  (сайт)   │   POST /api/cart/items      │  :8080   │ ◀───── │   :5432    │
│  :3000    │  ◀───────────────────────   └──────────┘        └────────────┘
└───────────┘        JSON-ответы
```

| Данные | Где хранились раньше | Где хранятся теперь |
|---|---|---|
| Товары, категории | Массив `PRODUCTS` в JavaScript | База данных → `GET /api/products` |
| Пользователи, пароли | `localStorage` (пароли в открытом виде!) | База данных, пароли как хеш BCrypt |
| Корзина залогиненного | `localStorage` | База данных → `/api/cart` |
| Корзина гостя | `localStorage` | `localStorage` (цены считает сервер) |
| Заказы | `localStorage` | База данных → `/api/orders` |
| Правила цен (скидки, доставка) | Функция `totals()` в JavaScript | Только на сервере (`PriceCalculator`) |
| Список избранного, отзывы | `localStorage` | `localStorage` (так и задумано планом) |

### Почему это важно для QA

Теперь одно действие пользователя проходит через **все три слоя**. Например, клик «Place your order»:

1. **UI:** появляется страница подтверждения с номером заказа (это проверит Selenium);
2. **API:** уходит `POST /api/orders` → `201 Created` (это проверит REST Assured);
3. **База:** появляются строки в `orders` и `order_items`, а склад уменьшается (это проверит JDBC).

Именно на такой связке строятся end-to-end тесты на следующих шагах.

## 3. Как браузер общается с API

### `fetch`: запрос из JavaScript

В браузере есть встроенная функция `fetch`. Она отправляет HTTP-запрос так же, как Swagger или Postman, только из кода страницы:

```js
const response = await fetch('http://localhost:8080/api/products');
const data = await response.json();   // разбираем JSON-ответ в объект
```

### `async` / `await`: ожидание ответа

Ответ от сервера приходит **не мгновенно**. Слово `await` значит: «подожди ответа, потом продолжай». Функция, внутри которой есть `await`, помечается словом `async`. Пока она ждёт, страница не зависает: пользователь может кликать, крутится спиннер.

### Одна функция `api()` для всех запросов

Чтобы не повторять одно и то же в 20 местах, все запросы идут через одну функцию `api(method, path, body)`. Она:

1. добавляет адрес сервера из `config.js`;
2. добавляет заголовок `Content-Type: application/json`, если есть тело запроса;
3. добавляет `Authorization: Bearer <токен>`, если пользователь залогинен;
4. превращает JSON-ответ в объект;
5. если пришла ошибка (статус 4xx/5xx), выбрасывает `ApiError` с полями из единого формата ошибок backend:

```js
class ApiError extends Error {
  status        // HTTP-статус: 400, 401, 409... (0 = сервер вообще не ответил)
  message       // "Payment declined. Please use a different card."
  fieldErrors   // { "shippingAddress.zip": "ZIP code must be 5 digits" }
}
```

Пример использования:

```js
try {
  const order = await api('POST', '/api/orders', body);
  navigate('#/order/' + order.orderNumber);       // успех → страница подтверждения
} catch (e) {
  err.textContent = e.message;                    // ошибка → показываем текст от сервера
}
```

> 💡 Вот где окупился единый формат ошибок из шага 1. Сайт **не придумывает** свои тексты ошибок, а показывает то, что прислал сервер. Если сервер вернул «Only 2 item(s) available in stock», пользователь видит именно это.

### `config.js`: где находится API

```js
window.SHOPLAB_CONFIG = {
  apiUrl: 'http://localhost:8080'
};
```

`index.html` подключает этот файл первым и берёт из него адрес. Чтобы направить сайт на другой сервер (например, в CI), достаточно поменять одну строку в `config.js`, не трогая основной код.

> **Почему `localhost:8080`, если сайт работает в Docker?** JavaScript выполняется **в вашем браузере**, а не внутри контейнера. Для браузера `localhost` — это ваш компьютер, а docker-compose пробрасывает порт 8080 backend на ваш компьютер.

### CORS: почему браузер разрешает запрос

Сайт открыт на `localhost:3000`, а API на `localhost:8080`. Для браузера это **разные источники** (origins), и по умолчанию он блокирует такие запросы. На шаге 1 мы настроили backend так, чтобы он отвечал браузеру: «запросы с `localhost:3000` разрешены». Теперь в этот список добавлен ещё порт `63342`, на котором IntelliJ показывает HTML-файлы.

## 4. Корзина гостя и залогиненного пользователя

Это самое интересное архитектурное решение шага.

### Проблема

- На исходном сайте добавлять товары в корзину можно **без входа**.
- API хранит корзину только для **залогиненных** пользователей (`/api/cart` требует токен).

Можно было заставить всех входить перед покупкой, но это ухудшило бы сайт и сломало бы существующие сценарии. Поэтому сделано так, как в настоящих магазинах (Amazon, Ozon):

### Решение

```
              ГОСТЬ                                     ЗАЛОГИНЕН
┌──────────────────────────────────┐      ┌──────────────────────────────────┐
│ Товары и количество хранятся в    │      │ Корзина хранится в базе данных    │
│ localStorage (shoplab_guestCart)  │      │ (таблицы carts, cart_items)       │
│                                   │      │                                   │
│ Цены и суммы спрашиваем у сервера:│      │ GET/POST/PUT/DELETE /api/cart...  │
│ POST /api/cart/preview            │      │                                   │
└────────────────┬──────────────────┘      └──────────────────────────────────┘
                 │  при входе (Sign in / Create account)
                 └──────────▶ каждый товар: POST /api/cart/items, промокод: POST /api/cart/promo
                              затем гостевая корзина очищается
```

### Новый эндпоинт `POST /api/cart/preview`

«Посчитай мне корзину, но ничего не сохраняй»:

```json
// запрос
{ "items": [{"productId": 7, "quantity": 2}], "promoCode": "QA10", "deliveryMethod": "STANDARD" }

// ответ: та же структура, что и у GET /api/cart
{ "items": [...], "subtotal": 79.98, "discount": 8.00, "shipping": 0.00, "total": 71.98, "amountToFreeShipping": 0.00 }
```

Благодаря ему **гость и залогиненный пользователь видят суммы, посчитанные одним и тем же кодом** на сервере. В JavaScript не осталось ни одного правила цен.

### Кто что проверяет

| Проверка | Гость | Залогиненный |
|---|---|---|
| Хватает ли товара на складе | Браузер (по данным с сервера) | Сервер (`409`) |
| Не больше 10 штук одного товара | Браузер | Сервер (`409`) |
| Промокод верный | Сервер (`preview` → `400`) | Сервер (`400`) |
| Суммы, скидка, доставка | Сервер (`preview`) | Сервер |
| Финальная проверка склада | Сервер при оформлении заказа | Сервер при оформлении заказа |

Гость не может оформить заказ без входа, поэтому **последнее слово всегда за сервером**.

## 5. Логин и токен в браузере

### Что происходит при входе

1. Браузер отправляет `POST /api/auth/login` с email и паролем.
2. Сервер отвечает токеном и данными пользователя.
3. Токен сохраняется в `localStorage` (ключ `shoplab_token`), чтобы пережить перезагрузку страницы.
4. Гостевая корзина переносится на сервер.
5. Во всех следующих запросах функция `api()` отправляет заголовок `Authorization: Bearer <токен>`.

### Что происходит при открытии сайта

```
есть сохранённый токен? ──нет──▶ пользователь — гость
        │ да
        ▼
GET /api/users/me ──200──▶ залогинен, в шапке «Hello, Standard»
        │ 401
        ▼
токен недействителен → тихо удаляем его, пользователь — гость
```

Раньше сайт просто «верил» тому, что записано в `localStorage`. Теперь он **спрашивает сервер**, действителен ли токен.

### Истёкшая сессия

Токен может стать недействительным, пока пользователь на сайте: сброс базы, выход на другом устройстве, удаление из таблицы `auth_tokens`. Тогда любой запрос вернёт `401`, и функция `api()`:

1. забывает токен;
2. показывает уведомление «Your session has expired. Please sign in again.»;
3. перенаправляет на страницу входа с `?redirect=...`, чтобы после входа вернуть пользователя туда, где он был.

👉 Хороший сценарий для UI-теста: «удалить токен в базе через JDBC → открыть Orders → оказаться на странице входа».

### Выход

`Sign out` вызывает `POST /api/auth/logout`, и сервер удаляет токен из базы. Даже если кто-то успел скопировать токен, он больше не работает.

## 6. Валидация на двух уровнях

Формы проверяются **дважды**:

| Уровень | Где | Зачем |
|---|---|---|
| 1. Браузер | JavaScript в `index.html` | Мгновенная подсказка, без запроса на сервер |
| 2. Сервер | Bean Validation в Java | **Защита.** Проверки в браузере можно обойти (DevTools, Postman, скрипт) |

Тексты ошибок одинаковые на обоих уровнях (договорились об этом на шаге 1).

Некоторые проверки возможны **только на сервере**:

- «An account with this email already exists»: только сервер знает, какие email заняты;
- «Payment declined»: только сервер «проводит» оплату;
- «Only N item(s) available»: склад мог измениться, пока вы заполняли форму.

### Как ошибки сервера попадают под нужные поля

Сервер возвращает `fieldErrors` с именами полей **API**, а на странице у полей свои `id`. Их связывает таблица соответствия:

```js
const CHECKOUT_FIELDS = {
  'shippingAddress.zip': 'zip',          // ошибка из API → поле с id="zip"
  'card.number':         'cardNumber',
  // ...
};
```

Функция `showFieldErrors` раскладывает ошибки по полям. Поэтому серверная ошибка выглядит так же, как браузерная: красная рамка и текст под полем.

## 7. Спиннеры, задержки и «гонки»

### Минимальные задержки сохранены

На исходном сайте задержки были искусственными: `setTimeout` на 600 мс в каталоге, 400 мс при входе, 1.5 с при оплате. Они нужны, чтобы **тренировать ожидания** в Selenium.

Настоящий сервер на `localhost` отвечает за 10–50 мс, и спиннер просто мелькал бы. Поэтому задержки сохранены как **минимальные**:

```js
const DELAY = {catalog: 600, login: 400, order: 1500};

// ждём ответ сервера, но не меньше 600 мс
data = await withMinDelay(api('GET', '/api/products?...'), DELAY.catalog);
```

Если сервер медленнее (как у `slow@shoplab.test`, 3 секунды), ждём столько, сколько отвечает сервер.

Ещё одно изменение: теперь **каждая** страница, которая загружает данные (корзина, заказы, товар, checkout), сначала показывает спиннер `loading-spinner`.

> ⚠️ Для будущих UI-тестов это значит, что почти любая страница появляется **не сразу**. Ищите элементы с явным ожиданием (`WebDriverWait`), а не сразу после перехода.

### Проблема «гонки» (race condition) и `renderToken`

Представьте: пользователь открыл каталог (запрос пошёл), но через 100 мс кликнул на товар (пошёл второй запрос). Ответ каталога приходит позже, и без защиты он **перерисовал бы страницу товара каталогом**.

Защита — счётчик `renderToken`. Он увеличивается при каждой смене страницы, а каждая страница перед отрисовкой проверяет, не устарела ли она:

```js
async function renderCart(){
  const token = renderToken;            // запомнили номер «своей» страницы
  const c = await loadCartView();       // ждём сервер...
  if (!isCurrent(token)) return;        // пользователь уже ушёл? Ничего не рисуем
  app.innerHTML = ...;
}
```

👉 Нестабильные (flaky) UI-тесты часто вызваны именно такими гонками, только в самом тесте: тест кликает раньше, чем страница готова. Хорошо понимать, откуда они берутся.

## 8. Что показывает сайт при ошибках

| Ситуация | Что видит пользователь | `data-testid` |
|---|---|---|
| Backend выключен при открытии сайта | Страница «The shop is not available» + кнопка «Try again» | `api-unavailable` |
| Ошибка при загрузке каталога, корзины, заказов | Красный блок с текстом ошибки | `api-error` |
| Ошибка действия (добавить в корзину и т. п.) | Всплывающее уведомление | `toast` |
| Ошибка в форме | Текст под полем | `<поле>-error` |
| Отклонена карта, нет на складе при заказе | Блок вверху checkout | `checkout-error` |
| Сессия истекла | Уведомление + страница входа | `toast`, `login-form` |

Раньше при любом сбое страница просто оставалась бы пустой. Понятное сообщение об ошибке — тоже часть качества продукта, и это можно тестировать.

## 10. Найденный баг в исходном сайте

Переписывая корзину, я нашёл ошибку в оригинальном коде. Оформлю её так, как оформляют баг-репорт:

> **Название:** Подсказка о бесплатной доставке обещает бесплатную доставку, но взимается $5.99
>
> **Серьёзность:** Major (пользователь видит неверную информацию о стоимости)
>
> **Шаги:**
> 1. Добавить в корзину «Selenium in Practice» ($39.99) и «Mystery at Harbor Lane» ($12.99). Сумма $52.98.
> 2. Применить промокод `QA10` (скидка $5.30, после скидки $47.68).
>
> **Ожидаемо:** «Add $2.32 more for FREE shipping», доставка $5.99.
>
> **Фактически:** «✔ Your order qualifies for FREE shipping», при этом в строке Shipping: **$5.99**.
>
> **Причина:** подсказка сравнивала с $50 сумму **до** скидки (`t.sub < 50`), а стоимость доставки считалась по сумме **после** скидки (`sub - discount >= 50`). Два правила для одного и того же — и они разошлись.

**Исправление:** подсказку теперь считает сервер тем же правилом, что и саму доставку (`PriceCalculator.amountToFreeShipping`).

👉 Отличный кандидат на автотест с граничными значениями. Сумма после скидки $49.99 → доставка платная, $50.00 → бесплатная.

## 11. Что изменилось в поведении сайта

Это важно знать, когда будете писать UI-тесты:

| Что | Было | Стало |
|---|---|---|
| Корзина после выхода | Оставалась в браузере | Пустая: корзина сохранена **в аккаунте** и вернётся после входа |
| Корзина на другом браузере | Не видна | Видна после входа: она на сервере |
| Порядок категорий в меню | Electronics, Books, Home… | По алфавиту (как отдаёт API): Books, Electronics, Fashion… |
| Кнопка «Reset store data» | Чистила `localStorage` | Сбрасывает **базу данных** (для всех!) и `localStorage` |
| Новые пользователи | Только в этом браузере | В базе, видны везде |
| Склад | Никогда не менялся | Уменьшается при заказе, возвращается при отмене |

> ⚠️ Поскольку данные теперь общие, тесты влияют друг на друга. Если один тест купил последние 2 робота-пылесоса, следующий тест их уже не купит. Поэтому на шаге 3 тесты будут сбрасывать базу через `POST /api/test/reset` перед запуском.

## 14. Проблемы, которые встретились по пути

**1. Запросы ушли раньше, чем backend запустился.**
После `docker compose up -d --build backend` я сразу отправил запросы и получил пустые ответы. Команда `up` дожидается **старта** контейнера, но не его **готовности**: Spring Boot запускается ещё 10–15 секунд.
**Решение:** ждать статуса `healthy` от healthcheck.
👉 **Урок для CI (шаг 7):** перед тестами нужно ждать готовности сервиса, а не просто запуска контейнера.

**2. Тест «после перезагрузки» на самом деле не перезагружал страницу.**
Мой скрипт переходил с `#/cart` на `#/`. Но если меняется только часть адреса после `#`, браузер **не перезагружает** страницу: срабатывает только событие `hashchange`. Поэтому проверка «подменённый токен при открытии сайта» на самом деле ничего не проверяла, а ещё три проверки упали следом.
**Решение:** настоящая перезагрузка (`Page.reload`).
👉 **Урок для UI-тестов:** `driver.get(url)` с тем же адресом, отличающимся только `#...`, — это **не** перезагрузка. Для перезагрузки есть `driver.navigate().refresh()`.

**3. База содержит ваши данные.**
Перед работой я заметил, что у товара 7 на складе 23, а не 25: вы оформляли заказы через Swagger. Поэтому я **не сбрасывал базу**, чтобы не стереть ваши данные. Мои проверки тоже создали несколько заказов (и сразу отменили их) для `standard@shoplab.test`.
Чтобы вернуть базу к исходному состоянию, нажмите в подвале сайта **«Reset store data»**.

## 15. Словарик

| Термин | Простыми словами |
|---|---|
| **fetch** | Встроенная функция браузера для HTTP-запросов из JavaScript |
| **async / await** | Способ написать «подожди ответа и продолжай» без зависания страницы |
| **Promise (промис)** | «Обещание» результата, который появится позже (ответ сервера) |
| **Origin (источник)** | Протокол + адрес + порт: `http://localhost:3000` и `http://localhost:8080` — разные источники |
| **CORS** | Правило браузера: сайт может обращаться к API другого источника, только если API это разрешил |
| **localStorage** | Небольшое хранилище браузера «ключ → значение», переживает перезагрузку. Видно в DevTools → Application |
| **Гостевая корзина** | Корзина посетителя без входа, хранится в браузере |
| **Race condition (гонка)** | Ошибка, когда результат зависит от того, какой из параллельных процессов закончится первым |
| **Flaky-тест** | Нестабильный тест: то проходит, то падает без изменений в коде. Частая причина — гонки и отсутствие ожиданий |
| **Headless-браузер** | Браузер без окна, управляется программой. Так UI-тесты запускаются в CI |
| **Chrome DevTools Protocol** | «Пульт управления» Chrome, через который работают инструменты автоматизации |
| **Single source of truth** | «Единственный источник правды»: каждое правило записано ровно в одном месте |
| **Валидация на клиенте / сервере** | Проверка данных в браузере (для удобства) и на сервере (для надёжности) |
