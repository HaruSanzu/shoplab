## 1. Общая картина

### Было → стало

**Было:** 144 API-теста. Они проверяют, что **ответил** сервер: «заказ создан, итог $71.98».

**Стало:** ещё **44 теста базы данных**. Они проверяют, что сервер **действительно сохранил**: строка в `orders` есть, итоги совпадают, склад уменьшился, пароль захеширован. Всего теперь **188 тестов**.

```
                1. действие через API (как пользователь)
┌──────────┐   POST /api/orders          ┌─────────┐        ┌────────────┐
│  тест    │ ──────────────────────────► │ backend │ ─────► │ PostgreSQL │
│          │ ◄────────────────────────── │  :8080  │        │   :5432    │
│          │   201 {"total": 71.98}      └─────────┘        └─────┬──────┘
│          │                                                      │
│          │   2. проверка через SQL (JDBC)                       │
│          │ ─────────────────────────────────────────────────────┘
│          │   SELECT total FROM orders WHERE order_number = ?
└──────────┘
```

### Зачем проверять базу, если API уже ответил «OK»?

API может **сказать** одно, а **сохранить** другое. Примеры таких багов, которые API-тест не увидит:

| Баг | API-ответ | Что в базе |
|---|---|---|
| Забыли сохранить изменение | `200`, товар в корзине | строки в `cart_items` нет: после перезагрузки страницы товар пропал |
| Пароль сохраняется открытым текстом | `201`, всё хорошо | `password_hash = 'Password123'` — утечка при взломе |
| Отказ банка, но склад уже списан | `402 Payment declined` | `stock` уменьшился, хотя заказа нет |
| Сохранён полный номер карты | `cardLast4: "4242"` | где-то лежит `4242424242424242` — нарушение правил PCI DSS |

DB-тесты — это взгляд «под капот». В вакансиях QA Automation часто пишут «SQL, проверка данных в БД»: это оно.

## 3. JDBC за 5 минут

**JDBC** (Java Database Connectivity) — стандартный способ работы с любой SQL-базой из Java. Шаги всегда одинаковые:

```java
// 1. Открыть соединение
try (Connection connection = DriverManager.getConnection(
             "jdbc:postgresql://localhost:5432/shoplab", "shoplab", "shoplab");
     // 2. Подготовить запрос: SQL с "?" вместо значений
     PreparedStatement statement = connection.prepareStatement(
             "SELECT stock FROM products WHERE id = ?")) {

    statement.setObject(1, 7);                       // 3. Подставить значение в первый "?"

    try (ResultSet rs = statement.executeQuery()) {  // 4. Выполнить
        while (rs.next()) {                          // 5. Читать строки по одной
            int stock = rs.getInt("stock");          //    взять колонку по имени
        }
    }
}   // 6. try-with-resources сам закроет всё, даже при ошибке
```

| Класс | Что это |
|---|---|
| `Connection` | Открытое соединение с базой (как открытый `psql`) |
| `PreparedStatement` | Подготовленный SQL-запрос с параметрами `?` |
| `ResultSet` | Результат запроса: «курсор», который идёт по строкам. `rs.next()` переходит к следующей строке и возвращает `false`, когда строки кончились |
| `SQLException` | Ошибка базы: нет соединения, неверный SQL, нарушено ограничение |

**JDBC URL** читается так: `jdbc:postgresql://localhost:5432/shoplab` = «через JDBC, база PostgreSQL, на компьютере localhost, порт 5432, база данных shoplab».

### Почему `?`, а не склейка строк (SQL-инъекция)

```java
// ПЛОХО: значение склеивается с SQL
"SELECT * FROM users WHERE email = '" + email + "'"

// Если email = "x' OR '1'='1", получится:
// SELECT * FROM users WHERE email = 'x' OR '1'='1'   ← вернёт ВСЕХ пользователей
```

```java
// ХОРОШО: значение передаётся отдельно от SQL
"SELECT * FROM users WHERE email = ?"   +   statement.setObject(1, email)
```

С `?` база получает SQL и значения **раздельно**, поэтому `x' OR '1'='1` — это просто странный email, а не кусок SQL. Это правило для любого кода, не только для тестов. Про SQL-инъекции любят спрашивать на собеседованиях QA.

## 4. Database: маленький помощник для JDBC

Код из раздела 3 длинный, и повторять его в каждом тесте неудобно. `Database` пишет его **один раз**:

| Метод | Что делает | Пример |
|---|---|---|
| `query(sql, mapper, params...)` | SELECT, много строк → `List<T>` | список строк корзины |
| `queryOne(sql, mapper, params...)` | SELECT, максимум одна строка → `Optional<T>` | пользователь по email |
| `count(sql, params...)` | `SELECT count(*)` → число | сколько заказов у пользователя |
| `update(sql, params...)` | INSERT / UPDATE / DELETE → сколько строк изменено | поменять цену товара |
| `checkConnection()` | проверить, что база доступна | в `@BeforeAll` |

### RowMapper: как строка таблицы превращается в объект

```java
Database.query("SELECT product_id, quantity FROM cart_items ...",
        rs -> new CartItemRow(rs.getLong("product_id"), rs.getInt("quantity")),
        email);
```

Лямбда `rs -> new CartItemRow(...)` — это **RowMapper**: «как из текущей строки `ResultSet` сделать Java-объект». `Database` сам крутит цикл `while (rs.next())` и вызывает её для каждой строки.

### Решения внутри Database

| Решение | Почему |
|---|---|
| Новое соединение на каждый запрос | Просто и надёжно: между тестами ничего не остаётся открытым. Пул соединений (HikariCP) быстрее, но для пары сотен запросов разница незаметна |
| `SQLException` → `DbException` | `SQLException` — *checked* исключение: без обёртки каждый тест пришлось бы помечать `throws SQLException`. `DbException` — *unchecked*, но хранит код ошибки `SQLState` |
| Каждый запрос прикрепляется к Allure | В отчёте рядом с HTTP-запросами видно, какой SQL выполнял тест и с какими параметрами |
| `queryOne` падает, если строк больше одной | Если «найти заказ по номеру» вдруг вернул 2 строки, это баг, и его нельзя молча скрыть |

### SQLState: коды ошибок базы

У SQL-баз есть стандартные 5-символьные коды ошибок. Тесты проверяют **код**, а не текст ошибки: текст может поменяться при обновлении PostgreSQL, а код — нет.

| Код | Название | Когда |
|---|---|---|
| `23505` | unique_violation | повтор значения в UNIQUE-колонке (второй такой же email) |
| `23514` | check_violation | нарушено CHECK-правило (`stock >= 0`) |
| `23503` | foreign_key_violation | ссылка на несуществующую строку (товар 999) |

## 5. ShopDb: все SQL-запросы в одном месте

`ShopDb` — это для базы то же, что API-клиенты для API (и Page Object для UI): тест вызывает **понятный метод**, а не пишет SQL.

```java
ShopDb.stockOf(Products.COFFEE_MAKER)      // вместо SELECT stock FROM products WHERE id = 12
ShopDb.cartItems(user.email())             // вместо JOIN трёх таблиц
ShopDb.order("SL-123456")                  // строка заказа или понятная ошибка «No order ...»
```

Если колонку переименуют, правится одно место, а не 30 тестов.

Пример запроса с `JOIN` (соединение таблиц):

```sql
SELECT ci.product_id, ci.quantity
FROM cart_items ci                       -- строки корзин
JOIN carts c ON c.id = ci.cart_id        -- → к какой корзине относится строка
JOIN users u ON u.id = c.user_id         -- → чья это корзина
WHERE lower(u.email) = lower(?)          -- только корзина нужного пользователя
ORDER BY ci.product_id
```

`ci`, `c`, `u` — короткие псевдонимы таблиц. `lower(...)` с обеих сторон — потому что email уникален без учёта регистра (так устроен уникальный индекс в базе).

### Строки как records (DbRows)

```java
public record OrderRow(long id, String orderNumber, long userId, String status, Instant createdAt, ...)
```

Имена полей повторяют **колонки** (`password_hash` → `passwordHash`, `shipping_cost` → `shippingCost`), а не JSON API. Это сделано специально: модели API (шаг 3) описывают то, что **показывает** сервер, а `DbRows` — то, что **хранится**. Например, в JSON поле называется `shipping`, а в таблице — `shipping_cost`.

### ShopDb только читает

Тесты меняют данные **через API**, как настоящий пользователь, а в базу только **смотрят**. Писать в базу напрямую (`Database.update`) можно лишь в двух случаях:

1. **Подготовить данные, которые API создать не умеет.** Например, у API нет эндпоинта «изменить цену», поэтому тест меняет цену через SQL (раздел 9).
2. **Проверить ограничения самой базы.** Тест пытается записать плохие данные и ожидает отказа (раздел 9).

## 6. Как устроен DB-тест

```java
@Test
@DisplayName("Placing an order decreases products.stock by the ordered quantity")
void orderDecreasesStock() {
    int stockBefore = ShopDb.stockOf(Products.COFFEE_MAKER);         // Arrange: запомнить «до»
    cart.addItem(Products.COFFEE_MAKER, 3).then().statusCode(200);

    placeOrder();                                                    // Act: действие через API

    assertThat(ShopDb.stockOf(Products.COFFEE_MAKER))                // Assert: проверка в базе
            .isEqualTo(stockBefore - 3);
}
```

Схема та же **AAA** (Arrange, Act, Assert), но проверка идёт через SQL.

### Цепочка подготовки

```
BaseTest          @BeforeAll: ждём API, POST /api/test/reset
   └── BaseDbTest @BeforeAll: Database.checkConnection()   ← понятная ошибка, если база недоступна
         └── OrdersDbTest @BeforeEach: новый пользователь, его CartClient и OrdersClient
```

JUnit сначала выполняет `@BeforeAll` родителя, потом наследника. Если база не запущена, тест сразу скажет:

```
Cannot connect to the database at jdbc:postgresql://localhost:5432/shoplab. Is the shop running? Start it with: docker compose up -d
```

Все приёмы независимости из шага 3 работают и здесь: новый пользователь на каждый тест, сравнение «до/после», сброс базы перед классом.

## 7. Теги: api и db не смешиваются

На шаге 3 вся подготовка (сброс базы, `expect`, `expectError`) жила в `BaseApiTest` с тегом `@Tag("api")`. Если бы DB-тесты унаследовались от него, они **тоже** получили бы тег `api` (теги наследуются), и `-Dgroups=api` запускал бы и их.

Поэтому общая часть вынесена в `BaseTest` **без тега**:

```
BaseTest                        (без тега: сброс базы, expect, expectError)
├── BaseApiTest   @Tag("api")   → ProductsApiTest, AuthApiTest, CartApiTest, OrdersApiTest
└── BaseDbTest    @Tag("db")    → UsersDbTest, CartDbTest, OrdersDbTest, SchemaDbTest
```

| Команда | Сколько тестов |
|---|---|
| `mvn -pl tests test` | 188 |
| `mvn -pl tests test -Dgroups=api` | 144 |
| `mvn -pl tests test -Dgroups=db` | 44 |
| `mvn -pl tests test -Dgroups=smoke` | 22 (13 API + 9 DB) |

Этот же `BaseTest` станет родителем UI-тестов на шаге 5.

## 9. Самые интересные тесты

### Откат транзакции: «всё или ничего»

```java
// В корзине: наушники (на складе много) + 3 книги (на складе 3)
// Кто-то другой успевает купить 1 книгу → осталось 2, а нам нужно 3
orders.place(TestData.cardOrder()).then().statusCode(409);

assertThat(ShopDb.stockOf(Products.HEADPHONES)).isEqualTo(headphonesBefore);  // наушники НЕ списаны
assertThat(ShopDb.stockOf(Products.LOW_STOCK_BOOK)).isEqualTo(booksBefore);
assertThat(ShopDb.countOrdersOf(user.email())).isZero();                      // заказа нет
```

Наушников хватало, но заказ целиком не прошёл, значит и наушники списываться **не должны**. Это и есть **транзакция**: все изменения сохраняются вместе или не сохраняется ни одно. API-тест такое не проверит: он видит только ответ `409`, а не склад наушников.

### Цена «замораживается» в момент покупки

```java
try {
    // У API нет эндпоинта «изменить цену», поэтому меняем её прямо в базе
    Database.update("UPDATE products SET price = ? WHERE id = ?", new BigDecimal("99.00"), Products.WALLET);

    // Старый заказ всё ещё по старой цене: и в базе, и в API
    assertThat(ShopDb.orderItems(orderNumber)).singleElement()
            .extracting(OrderItemRow::unitPrice).isEqualTo(new BigDecimal("32.00"));
} finally {
    // Вернуть цену ОБЯЗАТЕЛЬНО, даже если проверка выше упала
    Database.update("UPDATE products SET price = ? WHERE id = ?", originalPrice, Products.WALLET);
}
```

Два урока в одном тесте:
1. **Подготовка данных через базу** — обычная практика, когда через API нужное состояние не создать.
2. **`try / finally` для уборки**: блок `finally` выполняется всегда, даже если `assertThat` упал. Без него упавший тест оставил бы цену $99 следующим тестам.

### Полный номер карты нигде не хранится

```sql
SELECT count(*) FROM orders o WHERE o.order_number = ? AND o::text LIKE '%4242424242424242%'
```

`o::text` превращает **всю строку таблицы** в текст, и `LIKE` ищет в ней номер карты. Так проверяется не одна колонка, а сразу все: вдруг номер случайно попал в адрес или промокод.

### Ограничения базы: последняя линия обороны

```java
assertThatThrownBy(() -> Database.update("UPDATE products SET stock = -1 WHERE id = ?", 7))
        .isInstanceOf(DbException.class)
        .hasFieldOrPropertyWithValue("sqlState", DbException.CHECK_VIOLATION)   // 23514
        .hasMessageContaining("products_stock_check");
```

`assertThatThrownBy(...)` проверяет, что код **бросил исключение**. Даже если в Java-коде появится баг, который попробует уменьшить склад ниже нуля, база откажет. Плохие данные не записываются, поэтому убирать после таких тестов нечего.

### API и база показывают одно и то же время

```java
assertThat(row.createdAt()).isEqualTo(Instant.parse(api.createdAt()));
```

Это проверка бага №1 из шага 3 (наносекунды против микросекунд). Теперь он защищён тестом и на уровне базы: если баг вернётся, тест упадёт. Такой тест называется **регрессионным**.

## 10. Как проверить, что тест вообще умеет падать

Все 44 DB-теста прошли **с первого запуска**. Звучит хорошо, но это повод насторожиться: тест, который ни разу не падал, может ничего не проверять (например, проверка случайно сравнивает значение само с собой).

Поэтому я специально **сломал backend** и посмотрел, заметят ли тесты. Такой приём называется **мутационным тестированием** (вручную).

| Поломка | Что сделал | Результат |
|---|---|---|
| Корзина не очищается после заказа | закомментировал `cart.clear();` в `OrderService.placeOrder` | упал ровно `OrdersDbTest.orderEmptiesCart` ✅ |
| Склад не списывается при заказе | закомментировал `decreaseStock(...)` там же | упали 4 теста про склад ✅ (подробности в упражнении 11.5) |

После каждой проверки код возвращён на место (`git diff` пустой). Повторить это самому можно по [разделу 11](#11-как-запустить-и-проверить-руками).

## 11. Как запустить и проверить руками

### 2) Запустить тесты

```powershell
$env:JAVA_HOME = "$env:USERPROFILE\.jdks\openjdk-21.0.1"

```

Ожидаемо: `Tests run: 44, Failures: 0, Errors: 0, Skipped: 0` и `BUILD SUCCESS`.

### 3) Запустить из IntelliJ

1. Панель **Maven** → **Reload All Maven Projects** (подтянется драйвер PostgreSQL).
2. Откройте `tests/src/test/java/com/shoplab/tests/db/OrdersDbTest.java`.
3. Зелёный ▶ рядом с классом → **Run 'Orders (DB)'**.

### 4) Посмотреть в базу своими глазами

Так же, как это делают тесты. Подключитесь к базе:

```powershell
docker exec -it shoplab-postgres psql -U shoplab -d shoplab
```

**Пароли захешированы:**

```sql
select email, left(password_hash, 7) as hash_start, length(password_hash) as len from users order by id;
```

Ожидаемо: у всех `$2a$10$` и длина `60`. Это формат BCrypt: `2a` — версия алгоритма, `10` — «стоимость» (2¹⁰ раундов хеширования).

**Заказ и его строки** (сначала оформите заказ на сайте http://localhost:3000):

```sql
select o.order_number, o.status, o.subtotal, o.discount, o.shipping_cost, o.total,
       oi.product_title, oi.unit_price, oi.quantity
from orders o
join order_items oi on oi.order_id = o.id
order by o.id desc
limit 5;
```

**База сама защищает данные:**

```sql
update products set stock = -1 where id = 7;
```

Ожидаемо: `ERROR: new row for relation "products" violates check constraint "products_stock_check"`. Именно это проверяет тест `stockCannotBeNegative`.

Выход: `\q`.

### 5) Сломать backend и поймать поломку тестом (упражнение)

1. Откройте `backend/src/main/java/com/shoplab/order/OrderService.java`, найдите в методе `placeOrder` строку
   `item.getProduct().decreaseStock(item.getQuantity());` и закомментируйте её (`//` в начале).
2. Пересоберите backend: `docker compose up -d --build backend`.
3. Запустите: `mvn -pl tests test -Dgroups=db`.
4. Подумайте **до** запуска: какие тесты должны упасть? Затем сравните с результатом.
   Ожидаемо: падают **4** теста — `orderDecreasesStock`, `cancelRestoresStock`, `orderWholeStock`
   и `notEnoughStockChangesNothing`. Первые три очевидны: они проверяют склад.
   Четвёртый — сюрприз: без списания склада покупка другого пользователя не уменьшает число книг,
   поэтому наш заказ на 3 книги проходит (`201`) вместо ожидаемого `409`.
   Одна поломка в коде часто роняет тесты, которые на первый взгляд проверяют совсем другое.
5. **Верните** строку и пересоберите backend: `docker compose up -d --build backend`.

Ожидаемо: `Cannot connect to the database at jdbc:postgresql://localhost:5999/shoplab. Is the shop running?...`

## 13. Проблемы, которые встретились по пути

На этом шаге тесты не нашли багов в backend. Зато две ошибки были в **моих** тестах, и обе я заметил до первого запуска, при перечитывании кода. Обе типичны, поэтому стоит их разобрать.

**1. Два теста одного класса делили последний товар на складе.**
`orderWholeStock` выкупает оба робота-пылесоса (товар 15, на складе 2). `notEnoughStockChangesNothing` тоже рассчитывал на товар 15. JUnit **не обещает** порядок запуска тестовых методов: если второй тест выполнится после первого, товара уже не будет, и тест упадёт с непонятной ошибкой. Это заготовка flaky-теста.
**Решение:** второй тест использует другой товар — книгу «Mystery at Harbor Lane» (id 10, на складе 3). Для неё в `TestData` добавлена константа `LOW_STOCK_BOOK`.
**Урок:** сброс базы идёт один раз на класс, поэтому внутри класса тесты делят склад. Если тест **расходует** ограниченный ресурс, он должен расходовать свой.

**2. Тест ограничения, который прошёл бы по неправильной причине.**
Первая версия `orderStatusRestricted` делала `UPDATE orders SET status = 'SHIPPED'`. Но после сброса базы в этом классе нет ни одного заказа: `UPDATE` изменил бы **0 строк**, база не нашла бы что проверять, и ошибки не было бы. Тест упал бы с «исключение не брошено», хотя ограничение в базе работает.
**Решение:** тест сначала создаёт заказ через API и меняет статус именно ему.
**Урок:** для негативного теста проверьте, что «плохое действие» действительно выполняется.

**3. Тег `api` достался бы DB-тестам.**
Подготовка жила в `BaseApiTest` с `@Tag("api")`, а теги наследуются. Решение — общий `BaseTest` без тега (раздел 7).

## 14. Словарик

| Термин | Простыми словами |
|---|---|
| **JDBC** | Стандартный способ работы с SQL-базами из Java |
| **JDBC-драйвер** | Библиотека, которая учит JDBC разговаривать с конкретной базой (PostgreSQL, MySQL...) |
| **JDBC URL** | Адрес базы: `jdbc:postgresql://хост:порт/база` |
| **Connection** | Открытое соединение с базой |
| **PreparedStatement** | SQL-запрос с параметрами `?`, которые подставляются отдельно |
| **ResultSet** | Результат SELECT: курсор, который идёт по строкам |
| **RowMapper** | Функция «строка таблицы → Java-объект» |
| **SQL-инъекция** | Атака, при которой данные пользователя становятся частью SQL-запроса |
| **JOIN** | Соединение строк из нескольких таблиц по связи (`orders.user_id = users.id`) |
| **Транзакция** | Группа изменений, которые сохраняются все вместе или не сохраняется ни одно |
| **Откат (rollback)** | Отмена всех изменений транзакции при ошибке |
| **Constraint (ограничение)** | Правило в самой базе: `CHECK`, `UNIQUE`, `FOREIGN KEY`, `NOT NULL` |
| **Foreign key (внешний ключ)** | Колонка-ссылка на строку другой таблицы; база не даёт сослаться на несуществующую |
| **SQLState** | Стандартный 5-символьный код ошибки SQL (`23505`, `23514`...) |
| **BCrypt** | Медленный алгоритм хеширования паролей со встроенной солью |
| **Соль (salt)** | Случайная добавка к паролю перед хешированием: одинаковые пароли дают разные хеши |
| **Checked / unchecked исключение** | Checked нужно объявлять в `throws` или ловить; unchecked — не обязательно |
| **Регрессионный тест** | Тест, который защищает от возвращения уже исправленного бага |
| **Мутационное тестирование** | Специально внести ошибку в код и проверить, что тесты её поймают |
| **try / finally** | Блок `finally` выполняется всегда, даже после ошибки; нужен для уборки |
